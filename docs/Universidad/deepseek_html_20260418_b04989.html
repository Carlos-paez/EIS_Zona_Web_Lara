Fundamento

Introduccion

El desarrollo web en PHP ha evolucionado desde scripts monolíticos donde HTML, lógica de negocio y consultas SQL convivían en un mismo archivo. Esta práctica, conocida como codigo espagueti, hacía imposible mantener proyectos medianos sin generar bugs constantes.

El patron MVC (Modelo-Vista-Controlador) emerge como la solución arquitectónica que separa responsabilidades de forma clara, permitiendo que equipos trabajen en paralelo sobre las mismas capas sin conflictos.

Esta guia cubre MVC aplicado especificamente a PHP. No se asume experiencia previa con patrones de diseño, pero se requiere conocimiento basico de sintaxis PHP, HTML y SQL.

Problemas que resuelve MVC

Acoplamiento

Elimina la dependencia directa entre la logica de negocio y la presentacion. Un cambio en la interfaz no rompe las consultas a base de datos.

Duplicacion

Centraliza la logica de datos en un solo lugar. No necesitas copiar la misma consulta SQL en 5 archivos diferentes.

Colisiones

Permite que diseñadores trabajen en vistas mientras desarrolladores implementan controladores y modelos simultaneamente.

Referencia

Historia y Origen

MVC no nacio con la web. Su historia se extiende por mas de cuatro décadas de evolucion en la ingenieria de software.

1

1978 — Smalltalk-80 (Xerox PARC)

Trygve Reenskaug describe MVC por primera vez para Smalltalk. El objetivo era desacoplar la interfaz grafica de los objetos de dominio en aplicaciones de escritorio.

2

1996 — WebObjects (Apple/NeXT)

Apple adapta MVC para desarrollo web. WebObjects introduce Enterprise Objects Framework como la primera implementacion significativa de MVC en entornos HTTP.

3

2004 — Ruby on Rails

David Heinemeier Hansson populariza MVC masivamente con Rails. Su "convencion sobre configuracion" demuestra que MVC puede ser productivo y accesible.

4

2006 — Primeros frameworks PHP MVC

Zend Framework, CodeIgniter y CakePHP traen MVC al ecosistema PHP. Cada uno interpreta el patron de forma ligeramente distinta.

5

2011 — Laravel

Taylor Otwell lanza Laravel, que se convierte en el framework PHP mas popular. Su implementacion con Eloquent ORM, Blade y routing expresivo establece el estandar moderno.

6

2020+ — Evolucion hacia ADR

La comunidad PHP cuestiona si MVC es el patron ideal para HTTP. Surgen alternativas como Action-Domain-Responder, pero MVC sigue siendo dominante.

Comprender la historia de MVC ayuda a entender por qué existen variaciones del patron. No hay una implementacion "oficial": cada comunidad lo adapta a su paradigma.
Fundamento

Que es MVC Exactamente

MVC es un patron de arquitectura de software que divide una aplicacion en tres componentes interconectados con responsabilidades bien definidas. No es un framework, ni una libreria: es una convencion de organizacion de codigo.

Formalmente, MVC pertenece a la categoria de patrones de presentacion. Su objetivo primordial es la separacion de intereses (Separation of Concerns, SoC).

Definicion formal de cada componente

ComponenteResponsabilidadNo debe
ModelGestionar datos, reglas de negocio, validaciones y acceso a persistenciaConocer nada de HTML, HTTP requests o sesiones
ViewRenderizar la representacion visual de los datos del ModelEjecutar logica de negocio ni acceder a la base de datos
ControllerRecibir la solicitud HTTP, coordinar entre Model y ViewContener consultas SQL ni generar HTML directamente
El Controller es un coordinador, no un contenedor de logica. Un error frecuente es convertirlo en un "Fat Controller" que absorbe toda la logica que deberia estar en el Model.
Fundamento

Componentes en Profundidad

El Modelo — El corazon de la aplicacion

Representa la informacion con la que trabaja la aplicacion y las reglas que gobiernan su acceso y manipulacion. Es la unica capa que sabe "como" se almacenan y recuperan los datos.

Responsabilidades

  • Abstraccion de datos: Encapsular la estructura de tablas, colecciones o APIs externas
  • Reglas de negocio: Validar que un precio no sea negativo, que un email sea unico
  • Persistencia: CRUD completo sobre la fuente de datos
  • Transformacion: Convertir datos crudos en formatos utiles

Tipos de Modelos

TipoDescripcionEjemplo
Active RecordCada objeto representa una fila y maneja su propia persistenciaEloquent (Laravel), Yii AR
Data MapperObjetos de dominio separados de la logica de persistenciaDoctrine ORM, Spot ORM
Table Data GatewayUn gateway por tabla que maneja todas las operacionesZend_Db_Table
RepositoryColeccion-like que abstrae completamente la fuente de datosRepositories en Laravel/Doctrine

La Vista — Lo que ve el usuario

Responsable unicamente de presentar datos. Recibe variables del Controller y las renderiza en HTML, JSON, XML o cualquier formato de salida.

Responsabilidades

  • Presentacion: Convertir datos en markup HTML legible
  • Iteracion: Recorrer listas con bucles (foreach)
  • Plantillas: Herencia de layouts, inclusion de partials
  • Escapar salida: Prevenir XSS con htmlspecialchars()

Motores de plantillas comunes

MotorSintaxisCompila
Blade{{ $var }}, @ifSi, a PHP puro
Twig{{ var }}, {% if %}Si, a PHP puro
Smarty{$var}, {if}Si, a PHP puro
PHP puro<?php echo $var; ?>No needed
Regla de oro: La Vista NUNCA debe ejecutar INSERT, UPDATE, DELETE, ni llamar a $_POST directamente. Si tu vista contiene queries, no es MVC.

El Controlador — El coordinador

Punto de entrada de cada solicitud HTTP. Interpreta la peticion, delega al Modelo y selecciona la Vista. Es el "director de orquesta" que no toca ningun instrumento pero coordina a todos.

Ciclo de vida

  1. Recibir la solicitud HTTP (GET, POST, PUT, DELETE)
  2. Extraer parametros (de la URL, body, headers)
  3. Validar la solicitud (CSRF, autenticacion)
  4. Invocar al Modelo para obtener o modificar datos
  5. Pasar los datos a la Vista
  6. Retornar la respuesta HTTP

Controller por pagina

Un archivo por seccion: HomeController, UserController. Patron mas comun en frameworks modernos.

Controller por accion

Un archivo por accion individual (inspirado en ADR). Mas granular pero genera muchos archivos.

Thin Controller

El ideal: delega todo a Services/Use Cases. Solo orquesta, no piensa.

Practico

Flujo de Datos en MVC

En PHP, cada solicitud HTTP sigue un ciclo completo de vida:

1

El usuario envia una solicitud

El navegador realiza GET /usuarios/5. El servidor reenvia la solicitud a index.php (front controller).

2

El Router analiza la URL

Determina que UsuarioController y metodo ver($id) ejecutar, extrayendo $id = 5.

3

El Controller invoca al Model

$usuario = $usuarioModel->findById(5). El Modelo ejecuta la consulta SQL y retorna los datos.

4

El Controller pasa datos a la View

$this->render('usuarios/ver', ['usuario' => $usuario]). La Vista recibe la variable y renderiza HTML.

5

La respuesta se envia al navegador

El HTML renderizado se devuelve como respuesta HTTP con status 200. El ciclo termina. PHP libera memoria.

A diferencia de MVC de escritorio (donde el Model notifica a la View via Observer), en PHP web el flujo es unidireccional: Request → Controller → Model → View → Response. No hay estado persistente entre solicitudes.

Enrutamiento (Routing)

El enrutador traduce una URL en una llamada a un controlador especifico. Es el puente entre el servidor web y MVC.

core/Router.php
<?php
class Router
{
    protected $routes = [];

    public function get($path, $callback) {
        $this->routes['GET'][$path] = $callback;
    }

    public function post($path, $callback) {
        $this->routes['POST'][$path] = $callback;
    }

    public function dispatch() {
        $method = $_SERVER['REQUEST_METHOD'];
        $uri = parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH);

        // Buscar ruta con parametros: /usuarios/{id}
        foreach ($this->routes[$method] as $route => $callback) {
            $pattern = preg_replace('/\{[a-zA-Z]+\}/', '([a-zA-Z0-9]+)', $route);
            if (preg_match("#^{$pattern}$#", $uri, $matches)) {
                array_shift($matches);
                return call_user_func_array($callback, $matches);
            }
        }
        http_response_code(404);
        echo 'Pagina no encontrada';
    }
}
index.php — Uso del Router
<?php
require_once 'core/Router.php';
$router = new Router();
$router->get('/', [HomeController::class, 'index']);
$router->get('/usuarios/{id}', [UsuarioController::class, 'ver']);
$router->post('/usuarios', [UsuarioController::class, 'crear']);
$router->dispatch();
En produccion, .htaccess (Apache) o la configuracion de Nginx debe redirigir todas las solicitudes a index.php. Esto se conoce como Front Controller Pattern.

Implementando el Modelo

El Modelo base proporciona la conexion a la BD y metodos CRUD genericos. Los modelos especificos heredan de esta base.

core/Model.php
<?php
abstract class Model
{
    protected static $db;
    protected static $table = '';

    public static function getDb() {
        if (self::$db === null) {
            $cfg = require 'config/database.php';
            self::$db = new PDO(
                "mysql:host={$cfg['host']};dbname={$cfg['dbname']};charset=utf8mb4",
                $cfg['user'], $cfg['pass'],
                [PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION]
            );
        }
        return self::$db;
    }

    public static function all(): array {
        $stmt = self::getDb()->query("SELECT * FROM " . self::$table);
        return $stmt->fetchAll(PDO::FETCH_ASSOC);
    }

    public static function findById($id): ?array {
        $stmt = self::getDb()->prepare("SELECT * FROM ".self::$table." WHERE id=:id");
        $stmt->execute([':id'=>$id]);
        $r = $stmt->fetch(PDO::FETCH_ASSOC);
        return $r ?: null;
    }

    public static function create(array $data): int {
        $cols = implode(', ', array_keys($data));
        $ph = implode(', ', array_map(fn($k)=>":{$k}", array_keys($data)));
        $stmt = self::getDb()->prepare("INSERT INTO ".self::$table." ({$cols}) VALUES ({$ph})");
        $stmt->execute($data);
        return (int)self::getDb()->lastInsertId();
    }
}
app/models/Usuario.php
<?php
class Usuario extends Model
{
    protected static $table = 'usuarios';

    public static function validar(array $data): array {
        $err = [];
        if (empty($data['nombre'])) $err[] = 'Nombre obligatorio';
        if (!filter_var($data['email'], FILTER_VALIDATE_EMAIL))
            $err[] = 'Email invalido';
        return $err;
    }

    public static function registrar(array $data): array {
        $errores = self::validar($data);
        if (!empty($errores))
            return ['exito'=>false, 'errores'=>$errores];
        $data['password'] = password_hash($data['password'], PASSWORD_BCRYPT);
        $id = self::create($data);
        return ['exito'=>true, 'id'=>$id];
    }
}

Implementando el Controlador

core/Controller.php
<?php
class Controller
{
    protected function render(string $view, array $data = []) {
        extract($data); // Variables disponibles en la vista
        ob_start();
        $contentFile = "app/views/{$view}.php";
        if (!file_exists($contentFile))
            throw new Exception("Vista no encontrada: {$view}");
        require $contentFile;
        $content = ob_get_clean();
        require 'app/views/layouts/main.php';
    }

    protected function json($data, int $status = 200) {
        http_response_code($status);
        header('Content-Type: application/json');
        echo json_encode($data); exit;
    }

    protected function redirect(string $url) {
        header("Location: {$url}"); exit;
    }
}
app/controllers/UsuarioController.php
<?php
class UsuarioController extends Controller
{
    // GET /usuarios
    public function index() {
        $usuarios = Usuario::all();
        $this->render('usuarios/index', [
            'titulo' => 'Usuarios',
            'usuarios' => $usuarios
        ]);
    }

    // GET /usuarios/{id}
    public function ver($id) {
        $usuario = Usuario::findById($id);
        if (!$usuario) { http_response_code(404); echo 'No encontrado'; return; }
        $this->render('usuarios/ver', ['usuario' => $usuario]);
    }

    // POST /usuarios
    public function crear() {
        $data = ['nombre'=>$_POST['nombre']??'', 'email'=>$_POST['email']??''];
        $res = Usuario::registrar($data);
        if ($res['exito']) $this->redirect('/usuarios');
        else $this->render('usuarios/crear', ['errores'=>$res['errores']]);
    }
}

Ejemplo Completo: CRUD de Productos

database.sql
CREATE TABLE productos (
    id          INT AUTO_INCREMENT PRIMARY KEY,
    nombre      VARCHAR(150) NOT NULL,
    descripcion TEXT,
    precio      DECIMAL(10,2) NOT NULL DEFAULT 0.00,
    stock       INT NOT NULL DEFAULT 0,
    categoria   VARCHAR(100),
    creado_en   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
app/models/Producto.php
<?php
class Producto extends Model {
    protected static $table = 'productos';

    public static function buscarPorCategoria(string $cat): array {
        $stmt = self::getDb()->prepare("SELECT * FROM productos WHERE categoria=:cat ORDER BY precio");
        $stmt->execute([':cat'=>$cat]);
        return $stmt->fetchAll(PDO::FETCH_ASSOC);
    }

    public static function actualizar(int $id, array $data): bool {
        $sets = implode(', ', array_map(fn($k)=>"{$k}=:{$k}", array_keys($data)));
        $data['id'] = $id;
        $stmt = self::getDb()->prepare("UPDATE productos SET {$sets} WHERE id=:id");
        return $stmt->execute($data);
    }
}
Nota como el Modelo contiene toda la logica de acceso a datos y validacion. El Controlador no tiene ni una sola consulta SQL. Esta separacion es el nucleo de MVC.

Buenas Practicas en MVC con PHP

Thin Controllers, Fat Models

Los controladores deben ser lo mas delgados posible. Toda la logica de negocio pertenece al Modelo o a clases de servicio. Un controlador ideal tiene menos de 30 lineas por accion.

Mal: 15 lineas de validacion + consulta SQL directamente en el controller.

Bien: $resultado = Usuario::registrar($data); — una sola linea que delega todo.

Usar PDO con Prepared Statements

Nunca interpolar variables directamente en consultas SQL. Siempre usar prepared statements con PDO. Esto previene inyeccion SQL independientemente de la entrada del usuario.

Autoloading con Composer (PSR-4)

En lugar de require_once manual, usa Composer con el estandar PSR-4. Define un namespace como App\Controllers mapeado a app/controllers y deja que Composer resuelva las clases automaticamente.

Principio de Responsabilidad Unica (SRP)

Cada clase debe tener una unica razon para cambiar. Si tu modelo Usuario maneja tanto autenticacion como envio de emails, dividelo en: Usuario, AuthService, EmailService.

Inyeccion de dependencias

En lugar de crear dependencias dentro del controlador, inyectalas via el constructor. Esto hace el codigo testeable, flexible y desacoplado.

Manejo de errores centralizado

Implementa un set_exception_handler global que capture excepciones no manejadas. Muestra pagina amigable en produccion, detalles en desarrollo. Nunca expongas stack traces en produccion.

Patrones Relacionados con MVC

Front Controller

Todas las solicitudes pasan por un unico index.php. Hace posible el enrutamiento en MVC web.

Repository

Capa de abstraccion entre Model y BD. Facilita cambiar de BD sin tocar el Modelo.

Template Method

El layout define estructura (header/footer), las vistas llenan el contenido.

Dependency Injection

Controladores reciben dependencias via constructor. Mejora testabilidad.

Middleware

Capas interceptoras: auth, CORS, rate limiting. Se ejecutan antes/despues del controller.

Observer

El Model notifica a las Views cuando cambian datos. Mas usado en MVC de escritorio.

Frameworks PHP que Implementan MVC

Laravel

El framework PHP mas popular. Eloquent ORM (Active Record), Blade, artisan CLI, migraciones, seeders y ecosistema enorme.

Laravel — Controller + View
// app/Http/Controllers/ProductoController.php
public function index() {
    $productos = Producto::with('categoria')->orderBy('precio')->paginate(15);
    return view('productos.index', compact('productos'));

// resources/views/productos/index.blade.php
@foreach ($productos as $p)
    <h2>{{ $p->nombre }} — ${{ $p->precio }}</h2>

Symfony

Framework enterprise con componentes reutilizables. Mas estricto y configurable que Laravel. Usa Doctrine ORM (Data Mapper) por defecto y Twig como motor de plantillas.

public function index(ProductoRepository $repo): Response {
    $productos = $repo->findAll();
    return $this->render('producto/index.html.twig', [
        'productos' => $productos
    ]);
}

CodeIgniter

Framework ligero, rapido de aprender. Ideal para proyectos pequenos y medianos. MVC explicito y simple sin demasiada magia.
